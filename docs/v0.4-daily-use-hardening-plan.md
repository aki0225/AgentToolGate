## 1. 目标

`v0.4` 不扩展企业级功能，重点把 AgentToolGate 做成更可靠、低干扰的个人开发
guardrail：

- 普通开发命令保持静默和低延迟。
- `live` 模式不会因重启、服务退出或 Hook 输入异常而悄悄失效。
- 项目保护规则容易校验和解释，不要求使用者手工猜 JSON。
- HTTP / MCP 出站不会因为 DNS、代理、响应体或 Secret 脱敏缺口扩大风险。
- Windows 和 Linux 的核心路径进入自动化门禁。
- 发布证据能清楚区分产品版本、来源提交和证明范围。

项目定位保持不变：ATG 是工具调用治理网关和客户端 Hook guardrail，不是 OS
sandbox、EDR 或完整 DLP。

## 2. 实施原则

1. 每个安全修复先补能复现问题的失败测试，再修改实现。
2. 不通过放宽 Guard Core、项目保护规则或 expected decision 换取测试通过。
3. `off` 始终可恢复开发；`dry-run` 不阻断；只有 `live` 执行实时治理。
4. 性能优化必须通过危险动作、普通开发和治理不变量三套评估。
5. 每个阶段独立提交；前一阶段门禁通过后再进入下一阶段。
6. 所有临时二进制、数据库、日志和证据写入仓库忽略的 `.tmp/`。

### 阶段 1：本地运行和 Hook 生命周期

状态：已完成。

范围：

- `verify-local.ps1` 只停止本次脚本启动的 PostgreSQL。
- Hook matcher 覆盖 Bridge 已支持的全部工具别名。
- `hook control` 支持 `--dir <project>`。
- 明确运行时模式与项目持久模式的关系，禁止重启后无提示降级。
- 服务停止后不留下误导性的 `live` 状态；`doctor` 显示 endpoint 可达性。
- `live` 下非法 JSON、非对象或缺少工具名时保守拒绝并写脱敏诊断。
- Windows 支持 `python` 和 `py -3`，初始化阶段检查 Python 3.10+。

验收：

- 用户原本运行的 PostgreSQL 在 `verify-local -WithPostgres` 后仍保持运行。
- 从任意目录可分别控制两个仓库，且不会修改错误仓库的 control。
- 服务停止后 control 自动恢复，或 `doctor` 明确显示 `live but unreachable`。
- `live` 下截断 JSON、数组、空输入和缺少工具名均被阻断。
- `off` / `dry-run` 的低干扰行为不变。
- Codex、Claude Hook 测试和后端全量测试通过。

完成记录：

- `hook control --dir` 绑定显式项目，不再回落到外层 control。
- 正常停止写回 `off`；重叠实例恢复仍可达的前一实例；异常退出保留
  `live` / `dry-run` 以触发离线保守路径。
- `doctor` 和 status 的 endpoint 探测不跟随重定向。
- `live` 下非法 JSON、非对象、非法工作目录和缺少工具名均最小化拒绝。
- Codex / Claude Hook、PostgreSQL 生命周期、后端全量测试及 `go vet` 已通过。

### 阶段 2：Secret、HTTP 与 MCP 出站边界

范围：

- resolved Secret 即使被前后字符拼接也必须脱敏。
- Telemetry URL 不记录 query、fragment 或可能携带凭据的敏感路径。
- HTTP 在 DNS 解析后拒绝 loopback、metadata 和未授权私网地址。
- redirect 对目标 host 和解析结果重新检查。
- MCP Outbound 强制部署级 host ceiling，禁用隐式环境代理。
- 带 Secret 的 MCP 目标默认要求 HTTPS，仅允许显式 loopback 开发例外。
- 为 SSE 单行、事件、POST body、JSON-RPC result、工具数量和 schema 设置上限。

验收：

- Secret 不出现在 API response、audit、日志或 OTel。
- allowlisted 域名解析到 `169.254.0.0/16`、loopback 或未授权私网时目标零请求。
- 恶意代理环境不能改变实际 MCP 目标。
- 超限 MCP 响应快速失败、连接关闭且不持久化部分工具。
- HTTP、MCP、审批重验证和全量后端测试通过。

### 阶段 3：项目规则易用性与 Hook 性能

范围：

- 为 `.agenttoolgate/config.json` 和 `protected.json` 提供 JSON Schema。
- 新增项目配置 `validate` 命令。
- 新增只读 `explain` 命令，输出匹配规则、规范化目标、风险和最终决策。
- 建立 Windows / Linux 的 Hook 延迟基线。
- 在 Guard 语义等价的前提下减少每次 Hook 启动 Go CLI 的额外开销。

验收：

- 非法字段、路径逃逸、冲突规则和未知 action 在执行前给出明确错误。
- `explain` 不调用真实 Connector，不写审批，不产生目标副作用。
- 普通 `git status`、`git diff`、仓库内 `rg` 和普通文件读写保持 silent allow。
- 危险动作和治理不变量评估结果不变。
- Windows live Hook p95 不高于 250ms，目标低于 200ms。

### 阶段 4：审批体验、CI、Release 与文档

范围：

- 审批列表增加有界查询、状态过滤和稳定的 `callId` 审计入口。
- 审批失败区分过期、并发消费、权限不足、Connector 失败和服务不可达。
- CI 增加 Windows 后端测试。
- Connector E2E 和 PostgreSQL 多 Actor 审批进入自动化门禁。
- Release 校验 SemVer 标签、标签提交和打包提交一致。
- 增加 `.dockerignore`，统一 Docker、CI 和 Release 的 Node 版本。
- 前端停止跟踪会遮蔽 `vite.config.ts` 的生成文件。
- 真实 Codex 证据生成脚本的单元测试进入 CI。
- 修正贡献环境版本、历史文档状态、示例协议口径和证据索引。

验收：

- 1,000 条审批下首屏查询有界，任意审批可以打开对应审计。
- Windows / Linux、SQLite / PostgreSQL 和核心 E2E 门禁均通过。
- Release workflow 拒绝不存在、非 SemVer 或指向错误提交的标签。
- Docker context 不包含 `.env`、`node_modules`、测试结果或 `.tmp`。
- README、当前状态、证据索引和版本验收之间不存在“当前版本”冲突。

## 4. 明确暂缓

以下内容不属于 `v0.4`：

- KMS / Vault。
- GitHub App installation token 完整生产链。
- 企业级 object-level RBAC 和职责分离。
- SIEM、Slack 或 Teams 审批。
- 完整 MCP OAuth、Dynamic Client Registration 和 Outbound Streamable HTTP。
- macOS / ARM 正式 Release。
- 复杂规则管理 UI。
- OS sandbox、内核级 enforcement 或完整 DLP。

这些能力只有在实际用户需求出现后再评估，不作为当前版本完成条件。

## 5. 停止条件

满足以下条件后停止继续扩展功能：

- Full Access 下普通开发保持低干扰，高危动作稳定拦截。
- 多仓库切换、服务退出和异常 Hook 输入不存在静默失效。
- Secret、DNS、代理和 MCP 大响应边界有自动化测试。
- 项目保护规则可校验、可解释。
- Windows / Linux CI 和 Release 门禁稳定。
- 真实验收与公开文档能说明能力、证据和限制。
